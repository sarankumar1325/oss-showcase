# Plan: make the showcase usable by anyone

**Goal:** anyone can see their own merged open-source work in this site, either by **forking the repo** or by **typing their GitHub username** into a hosted copy. It keeps the cinematic experience and needs as little setup as possible.

**Status:** all five phases built: fork mode, the `?u=` viewer, the optional token and sharing polish. What's left is publishing the repo.

---

## 1. The key finding: you usually don't need a token

Everything the site shows is **public**: merged PRs, repo names, owners and avatars. GitHub serves all of it without authentication.

Checked against GitHub's docs (Nov 2026):

| | Without a token | With any token |
| --- | --- | --- |
| Search API (`/search/issues`) | 10 requests / min | 30 requests / min |
| Everything else (`/users/...`) | **60 requests / hour** | 5,000 requests / hour |
| GitHub Actions built-in `GITHUB_TOKEN` | — | 1,000 requests / hour per repo, **no setup needed** |
| Search results per query | max **1,000** | max **1,000** |

So a token raises rate limits. It does not unlock data.

**The smallest possible token:** a *fine-grained personal access token* with *Public repositories (read-only)* and **zero permissions** selected. GitHub's docs say every token always includes read-only access to all public repos. That token can't touch anything private, write anything, or act as the user. This is the only token we should ever ask for.

**The one rule that matters:** a token must **never** go into the built site. Vite bakes every `VITE_*` environment variable into the public JavaScript, where anyone can read it. A token lives either in a GitHub Actions secret (build time) or in the visitor's own browser storage (runtime). Never in the bundle, never in the repo.

## 2. Two ways people will use it

### A. Fork and deploy (recommended first)

1. Fork the repo.
2. Edit one file, `portfolio.config.ts` (username, display name, time zone).
3. Enable GitHub Pages. A scheduled GitHub Action:
   - runs a snapshot script with the **built-in `GITHUB_TOKEN`** (no secret to create),
   - writes `snapshot.json`,
   - builds and deploys.

The browser then polls for new merges without a token, as it does today. Visitors get the fast, cinematic first load from the snapshot, and the owner never handles a token.

### B. Hosted viewer: "type any username"

`yoursite.com/?u=octocat` (or a landing page with a username box) loads that person's work live in the browser. No token is needed. Each visitor's own IP gets the 60/hour and 10/min budget, so the cost doesn't pile up on one place.

An optional *Add a token* sheet raises those limits, which helps heavy contributors and people browsing many profiles:
- The token is stored only in that visitor's browser: `sessionStorage` by default, `localStorage` if they tick "Remember".
- It is sent only to `api.github.com`.
- It can be removed with one click.
- The sheet shows the remaining rate-limit budget so people can see why a token helps.

## 4. Hard problems and how to handle them

1. **The 1,000-result search cap.** Prolific contributors have more than 1,000 merged PRs. Split the query into date windows (`merged:2024-01-01..2024-06-30`, and so on) and merge the results. The snapshot script does this freely. Viewer mode does it lazily, newest window first.
2. **First load is slow without a token.** At 10 searches/min and 100 results per page, 1,000 PRs take about 10 requests, a minute or more. Turn the wait into the show: the intro's counter already counts up, so let it count up *as pages arrive*, with a real progress line. Cache each user's results in IndexedDB so returning visits are instant and fetch only what's new.
3. **Organization vs individual owner.** The search API doesn't say which an owner is. Looking each one up costs one request against the **60/hour** budget, and you have 112 owners. So:
   - Fork mode resolves owner types at build time.
   - Viewer mode resolves them lazily and caches them, and shows "owner" until it knows.
   - Viewer mode resolves them all at once if a token is present.
4. **Rate-limit UX.** The status pill already handles `limited` and `offline`. Add "resets in 4 min" from the `x-ratelimit-reset` header, and offer the token sheet at that moment, not before.
5. **Edge cases:**
   - Unknown username: 404 page with a search box.
   - Zero merged PRs: an honest empty state.
   - An organization account entered as a user.
   - Usernames validated as GitHub's 1–39 character rule before any request.
6. **What counts as "external".** Today `-user:handle` excludes your own repos. Some people also want to exclude employers' orgs. Add `config.excludeOwners: string[]`, and `?exclude=` in viewer mode.

## 5. Out of scope (deliberately)

- **Private contributions.** These would need a token with private repo read access, and publishing private PR titles on a public page is a leak waiting to happen. The site stays public-only, which is also why the minimal token is enough.
- **A backend.** Both modes run without a server. A small serverless proxy with its own token could come later, if the hosted viewer becomes popular enough to hit limits.

## 6. Build order

| Phase | What ships | Why this order |
| --- | --- | --- |
| **1. Config extraction** | `portfolio.config.ts`; time zone threaded through `format`/`derive`; all copy templated; avatar fallback | Everything else depends on it, and it's useful immediately for forks |
| **2. Snapshot script + Action** | `scripts/snapshot.ts` (Bun; date-windowed, owner types, writes JSON); `.github/workflows/deploy.yml` (daily cron, Pages deploy, built-in token) | Makes the fork path real: edit one file, enable Pages, done |
| **3. Viewer mode** | `?u=handle` route and landing box; loading pipeline driving the intro counter; IndexedDB cache; lazy owner types | The "anyone can view their work" tool |
| **4. Optional token** | Token sheet; storage choice; rate-limit meter; offered only when limited | Only matters once viewer mode exists |
| **5. Sharing polish** | Per-user page title, Open Graph card, "Fork this" button, README with a 3-step guide | Helps it spread |

Phases 1–2 are a solid release on their own. Phase 3 is the biggest piece of work.

## 7. Decisions needed from you

1. **Which mode first:** fork-and-deploy only, hosted viewer only, or both? I recommend both, fork first.
2. **Default time zone:** the visitor's own, or the profile owner's? I recommend the owner's from config, with the visitor's zone as the viewer-mode default.
3. **Own repos:** should they be excludable only, or also optionally included (some people want "all my merged PRs")?
4. **Name and license** for the public repo (MIT is the usual choice for templates like this).
